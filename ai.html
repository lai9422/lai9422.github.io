痛點一

即時性不足

情緒困擾往往在非預期的時間點發生，例如夜間或週末。

專業心理諮詢服務有固定工作時間，導致使用者在情緒低谷時難以即時獲得支援。

等待諮商期間，情緒可能持續惡化，錯過最佳介入時機。
痛點二

表達困難

許多人面對陌生人（即使是專業心理師）時，難以啟齒。

不知道從何說起自己的困擾，特別對於部分學生或高齡者，表達障礙可能更為顯著。

導致無法有效傳達自身狀態與需求。
痛點三

風險辨識挑戰

在大量對話中，潛在的自傷、他傷或危機訊號可能被忽略。

人工篩選耗時費力，且容易受主觀判斷影響，高風險個案無法被及時轉介。

系統需要自動化風險初篩機制。

模組一：PII 遮蔽

在數據進入處理流程前，移除所有可識別個人身份的資訊。

技術：NER + Regex
  • • 命名實體識別 (NER) 辨識人名、地名、組織名。
  • • 正則表達式 (Regex) 補強電話、信箱、身分證字號。
  • • 替換為通用標籤 (如 [姓名]、[電話])，保留語義。
從源頭保護隱私，確保後續處理數據已去識別化。

模組二：情緒分類

即時判斷使用者情緒狀態、壓力程度與潛在危機風險。

技術：mDeBERTa zero-shot
  • • 無需特定情緒標籤訓練數據，泛用性強。
  • • 輸出多維度標籤：焦慮、憂鬱、憤怒、絕望等。
  • • 設定危機閾值，觸發後續分流。
系統的「安全閥」— 第一時間辨識潛在危險。

模組三：RAG 檢索

為 LLM 提供外部知識，確保回覆專業性與一致性。

技術：text2vec + Faiss
  • • 知識庫：心理教育文章、校園資源、CBT 技巧。
  • • 向量化後儲存於 Faiss 向量資料庫。
  • • 即時檢索最相關片段，作為 LLM 上下文。
降低幻覺 (Hallucination)，提升回覆可信度。

模組四：回覆生成

生成支持性、專業且安全的心理回覆。

技術：Llama-Breeze2-8B (本地部署)
  • • 本地部署，數據不外流，隱私可控。
  • • CBT 提示詞引導結構化、問題解決導向回覆。
  • • 預設安全規則，避免不當或超出能力範圍之回覆。
提示工程 (Prompt Engineering) 是關鍵。

模組五：共情評估

確保 AI 回覆具備同理心且恰當。

技術：Embedding 相似度 + 規則
  • • 認知共情：使用者訊息與 AI 回覆的餘弦相似度。
  • • 情感共情：檢查是否包含情緒詞、肯定語句、反思。
  • • 綜合評分，低分觸發重新生成機制。
系統的「品質控制員」。

模組六：後台治理

專業人員可介入、可追蹤、可校準的治理機制。

技術：資料庫 + 審核佇列 (Review Queue)
  • • 高風險或低共情回覆自動推送至佇列。
  • • 心理師進行二次評估與人工介入。
  • • 校準模型判斷，形成持續改進迴圈。
確保系統不脫離專業監管。
核心流程

「先判斷，再生成」

使用者 PII 遮蔽 情緒分類 高風險？
是 → 危機提示 否 → RAG 檢索
LLM 生成 共情評估 發送 & 審核

步驟 1：使用者輸入 → PII 遮蔽

NER 與 Regex 協作，自動偵測並替換姓名、電話、地址、身分證字號。

原始：我叫王小明，電話是 0912-345-678。
遮蔽後：我叫 [姓名]，電話是 [電話]。

步驟 2：情緒分類判斷

mDeBERTa zero-shot 輸出情緒標籤 (焦慮、憂鬱等)、壓力指數、危機分數。

焦慮: 0.78絕望: 0.45自傷意圖: 0.12

分支：高風險 → 危機提示

當「自傷意圖 > 0.25」或危機分數超標，立即觸發。

  • • 系統優先生成包含求助資源的安全回覆。
  • • 提供生命線、心理諮詢專線等即時資訊。
  • • 對話自動推送至後台審核佇列。
確保高風險個案不被遺漏。

分支：低風險 → RAG 檢索

進入常規回覆生成流程。

  • • 根據使用者訊息與歷史摘要檢索知識庫。
  • • 檢索心理教育、CBT 技巧、校園資源。
  • • 提供 LLM 豐富的上下文資訊。
提升回覆的專業性與具體性。

步驟 3：LLM 生成回覆

Llama-Breeze2-8B 綜合考量：使用者訊息、情緒標籤、RAG 檢索結果、CBT 提示詞、安全規則。

CBT 引導支持性安全優先

步驟 4：共情評估門控

生成後不立即發送，先通過品質門控。

  • • 認知共情分數 (語義理解)。
  • • 情感共情分數 (情緒回應)。
  • • 加權計算總分，低於閾值觸發重試。
避免將機械式回覆傳送給使用者。

低共情 → 重新生成機制

當共情分數未達標，系統自動校準。

  • • 原始提示詞加上「更強同理心」指令。
  • • 再次送入 LLM 重新生成。
  • • 最多重試 2 次，確保品質。
內建的品質控制環節。

步驟 5：去識別化儲存與審查佇列

  • • 所有對話紀錄去識別化後寫入 history.db。
  • • 高風險與低共情回覆推送至審核佇列。
  • • 專業人員介入追蹤與校準。
技術區分

情緒分析 vs 共情計算

情緒分析

判斷使用者狀態，啟動危機提示。對象：使用者訊息。

安全閥

共情計算

評估 AI 回覆品質，低分重新生成。對象：訊息+回覆配對。

品質控制員

最佳整合策略：風險與品質分離

  • ✓ 風險判斷不被回覆品質污染。
  • ✓ 即使 AI 回覆不夠共情，高風險仍優先處理。
  • ✓ 共情評估專注於提升回覆溫度。
  • ✓ 降低誤報，提升系統穩定性。
隱私保護

多層次隱私工程

PII 遮蔽 (NER+Regex)
加鹽雜湊 (Salted Hash)
資料庫分離 (identity.db / history.db)
差分隱私 (Differential Privacy)

PII 遮蔽詳情

使用者訊息進入系統的第一步即進行遮蔽。

  • • NER 辨識人名、地名、組織名。
  • • Regex 匹配電話、信箱、身分證字號。
  • • 替換為 `[姓名]`、`[電話]` 等通用標籤。
確保 AI 模型無法接觸到可直接識別身份的資訊。

加鹽雜湊 (Salted Hash)

外部平台 user_id 不直接儲存，經加鹽雜湊生成 internal_uid。

  • • 加入隨機字串 (Salt) 再進行雜湊。
  • • 單向不可逆，即使資料庫洩露也無法反推。
  • • 切斷內部數據與外部真實身份的連結。
確保內部識別符號無法逆推出真實使用者。

資料庫分離

identity.db

internal_uid + 匿名元數據

history.db

去識別化對話 + 情緒標籤

單一資料庫被洩露也無法拼湊完整個人樣貌。

差分隱私 (Differential Privacy)

統計輸出中加入適量隨機雜訊 (Laplace noise)。

  • • 單一使用者數據變化對最終結果影響極小。
  • • 無法判斷特定使用者是否包含在數據集中。
  • • 保護個體隱私，同時保留群體趨勢價值。
支援公共心理健康決策，不犧牲隱私。
並發設計

並發處理的挑戰

Thread 暴增

100人同時請求瞬間產生大量執行緒，導致 OOM。

GPU 競爭

多請求競爭 GPU，頻繁上下文切換，利用率下降。

鎖競爭

共享資源鎖 (LLM) 導致序列化，吞吐量受限。

解決方案：ThreadPool + Queue + 鎖分離

  • • ThreadPoolExecutor：固定執行緒池 (max_workers=8)，限制並行數量。
  • • 工作佇列 (Queue)：吸收瞬間流量高峰，平滑負載。
  • • 鎖分離：emotion_lock (CPU) 與 llm_lock (GPU) 分離，最大化並行。
目標：穩定吞吐量與可預測延遲，支援 100 人同時使用。
